# 下线功能需求留档(2026-08-31)

> **这篇解决什么问题、写给谁**:2026-08-31 经用户决策,所有"假功能"(stub / 硬编码模板 / mock
> 数据冒充真实能力的呈现)整体下线,系统只保留真实跑通的核心闭环。本文逐项留档:原始产品需求、
> 已有可复用资产、为什么下线、**重启验收条件与操作步骤**——后面继续实现时以本文为起点,
> 不需要重新考古。
>
> 下线执行的代码改动见当日提交(main);功能开关目录 `apps/server/src/features/feature-catalog.ts`
> 与管理端「实验室管理」页仍登记全部条目。

## 判定口径

「假功能」= 用户在真实模式下会看到、但背后是 stub/模板/mock 的能力呈现。真实数据的聚合统计
(学生今日/周报、教师学情热力、管理端 dashboard)经核查**全部真查库**,不在下线范围。
AI 答疑(qa)为**真实接入**(配 `LLM_API_KEY` 即走真实供应商),不下线;无 key 时路由自动走 mock
且回复带「mock」字样,部署时务必配 key(见部署手册/验收指引)。

## 1. AI 生成课件(含真实生图)· `ai_courseware`

**原始需求**:教师贴文字稿 → 文本 LLM 逐页大纲 → 逐页编辑确认 → 生图模型逐页生成整页幻灯片
→ 成品落资源库(type=ppt),可挂讲次环节,课堂随快照下发整页图。

**已有资产(全链路代码在,质量较高)**:
- 契约 4 端点(`POST /courseware/outline`、`POST /courseware/jobs`、`GET/POST /courseware/jobs/{jobId}[/retry]`)+ 4 DTO;
- 服务端 `apps/server/src/courseware/**`(大纲 LLM、BullMQ 队列逐页生图、任务态 Redis 24h、成品落 Resource);
- 生图供应商适配 `ai/llm/providers/*image*`(`IMAGE_*` env 独立配置,mock_image 基线);
- 教师端向导页 `apps/teacher/src/pages/courseware/**`(FeatureGuard 门禁完备);
- e2e:courseware 套件 14 用例(mock 链路全绿)。

**为什么下线**:真实生图链路从未真机验证(默认 mock 生图,成品是占位图);课堂整页图
(`CoursewarePageView.imageUrl`)学生端未接线(UI 不读该字段)——即"能走完流程但产物是假的"。

**下线方式(已执行)**:
- `feature-catalog.ts` 的 `ai_courseware` `defaultStage: 'beta' → 'off'`(4 端点 4701 硬门禁,教师端入口整体消失);
- 课堂快照组装排除历史已挂讲次的 ai_courseware 资源(`classroom.service.ts` buildCourseware,含移除整页图签名逻辑),课堂零残留;
- 资源库中历史成品仍在(带「AI 生成」标签,可手动删除)。

**重启验收条件**(即 catalog 里的 acceptance):
1. 配真实 `IMAGE_API_KEY` 后真机走通:贴稿 → 大纲 → 逐页生图 → 落库,图为真实内容非占位;
2. 学生课堂讲解页接线 `imageUrl` 渲染整页图(恢复课堂组装的签名逻辑,git 历史可寻)并真机走查;
3. 失败路径(生图失败 → failed 页 → retry)真机验证;额度计量(ai_calls)按上游实际值记账。

**重启操作**:管理端「实验室管理」把 ai_courseware 切 beta(白名单试用)→ 验收后 ga;
课堂组装的过滤与签名代码按上面第 2 条恢复。

## 2. 拍照/公式 AI 预批 · `photo_pregrade`(此前已 off,维持)

**原始需求**:学生解答题拍照(或公式作答)提交 → OCR 识别 → LLM 按 rubric 逐步预批
→ 教师复核采纳出分(减轻批改负担)。

**已有资产**:预批队列全链路(`grading/pre-grading.queue.ts`,BullMQ 并发 5)、
`ai/features/pre-grading.gateway.ts`(LLM 预批,JSON Schema 严格校验)、教师复核 UI
(`GradingReviewPage`,aiScore/aiSteps 展示)、学生端预批结果卡(`PreGradeCard`,门禁隐藏中)。

**为什么下线**:OCR 是 stub(`ai/ocr/ocr.service.ts` LocalOcrStub,输出「【本地OCR占位】」),
拍照内容根本没被识别,预批分是假的。技术路线已定 Qwen3-VL 自托管(见 `_research/评审稿`)。

**下线状态**:catalog off(E1 已做,维持)+ 机构设置页「公式题 AI 预批」开关改为「已下线」登记态
(原开关被 flag AND 逻辑架空)。拍照上传本身是真功能,保留:学生仍可拍照提交,教师人工看图批改。

**重启验收条件**:接入真实 OCR/视觉模型;真实手写样本抽检预批准确率达标后先开 beta 白名单。

## 3. 课堂伴学旁白(narration)

**原始需求**:学生随堂作答后,AI 以「小启」人设即时给一句针对性旁白(答对鼓励/答错引导),
营造伴学感。

**下线前的假实现(已移除)**:双层模板——`org.settings.ai.classCompanion` 关时用 3 句硬编码兜底
(NARRATION 常量),开时走 `companion-templates.json` 模板拼句(占位变量常为空);学生端以
紫色渐变「✦ 小启」旁白条呈现,视觉上是 AI。**关开关也关不掉**,故属必下线。

**下线方式(已执行)**:服务端 `class:answer` 不再生成/emit 旁白(ack 的 `narration` 恒 null,
协议字段本就可空,`class:narration` 事件保留在 ws-protocol 未删);学生端底部旁白条组件
`ClassFoot` 删除;`seed`/`init:prod` 的 `classCompanion` 默认 false;机构设置页开关改「已下线」。

**可复用资产**:`ai/features/companion.service.ts`(narration 接口 + LLM 路由,含
`AI_COMPANION_USE_LLM` 开关)保留未删,是重启时的实现骨架;`segment_switch`/`idle` 模板
场景当时就未接线,重启时一并评估。

**重启验收条件**:走真实 LLM(`AI_COMPANION_USE_LLM=true` + 路由 real),旁白内容基于该题
上下文可被抽检认可;时延不阻塞作答(原 4s 超时设计可沿用);成本计入 ai_calls 额度。
**重启操作**:恢复 classroom.service 的 buildNarration 调用(git 历史)→ 学生端恢复旁白条
→ e2e a6 narration 用例改回。

## 4. AI 学情诊断 · diagnosis

**原始需求**:教师在学情分析页对单个学生一键生成诊断:近 30 天练习概况、薄弱知识点归因、
教学建议。

**下线前的假实现**:`AI_DIAGNOSIS_USE_LLM` 默认 false → `diagnosis-templates.json` 模板拼句
(统计数字真,文案是模板),教师端标着「AI」Tag 呈现;seed/init-prod 默认把机构开关打开。

**下线方式(已执行)**:`seed`/`init:prod` 的 `diagnosis` 默认 false(服务端端点本有
`org.settings.ai.diagnosis` 403 门禁);教师端学情分析页按 `me.orgSettings.ai.diagnosis`
条件渲染诊断按钮(默认不显示);机构设置页开关改「已下线」登记态(防止一键恢复假功能)。

**可复用资产**:`ai/features/diagnosis.service.ts`(真实统计取数 + LLM 路由完整,只差把
USE_LLM 打开接真模型);`weakPoints` 掌握度归因是真算的;`DiagnosisOutput.suggestion`
字段未透出 API(重启时补契约)。

**重启验收条件**:`AI_DIAGNOSIS_USE_LLM=true` + LLM key + 路由 real,诊断文案经真实数据抽检;
suggestion 字段透出契约;机构设置页恢复开关(或并入实验室功能分级)。
