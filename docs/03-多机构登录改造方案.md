## 一、现状与风险(基于 2026-08-31 代码核实)

两个登录入口都不带机构标识,跨机构定位全凭「全库搜」:

| 入口 | 现状逻辑(`apps/server/src/auth/auth.service.ts`) | 两机构并存时的坏情况 |
|---|---|---|
| `POST /auth/login`(管理员/教师,手机号+密码) | `runWithoutTenant` + `findFirst({ phone, role in [admin,teacher], active })` —— **首个命中即当事人** | 两机构存在同手机号教师:A 机构的教师被检索命中后,B 机构同号教师**永远无法登录**(密码不对则整体失败);若两人密码恰好相同则直接串进 A 机构 |
| `POST /auth/student/login`(学号+密码) | 全库取同 `studentNo` 候选,**逐个验密码**,首个验中即当事人 | 学号本就仅 org 内唯一(`@@unique([orgId, studentNo])`),跨机构撞号是常态;两个同号学生密码相同(如都用初始密码规则)→ 串进先建的机构。另:逐候选 argon2 验密是 O(n) 计时行为 |

配套事实:

- `orgs` 表**没有机构码字段**(id/name/status/settings,见 `prisma/schema.prisma` model Org)。
- `users.phone` 无任何唯一约束(仅 `@@unique([orgId, teacherNo/studentNo])`);
  **schema 注释写「应用层加密」但实为明文**——登录直接 `where: { phone: 原文 }`,
  全仓无 phone 加密代码。设计按明文现状走(见第三节 phoneHash 取舍);执行本方案时
  顺带把该误导注释改掉(schema 注释变更一并走本次批准)。
- JWT payload `{uid, orgId, role}` 与租户注入机制不用动:问题只在「登录时如何定位到人」。
- `devices` / `login_tickets` 表与本改造无耦合。

## 二、目标行为

- 登录请求显式携带**机构码 `orgCode`**,服务端先定位机构、再在机构内定位用户;
  跨机构同手机号/同学号完全隔离。
- 同一机构内手机号唯一(数据库约束兜底,不再依赖应用逻辑自觉)。
- 学生登录在机构内按学号**唯一命中**(复合唯一保证),密码只验一次,消除 O(n) 验密。

## 三、改造设计

### 3.1 schema(迁移 0005,两张表)

```prisma
model Org {
  // 新增:登录用机构码,全局唯一;仅字母数字,大小写不敏感建议存大写
  code String @unique @db.VarChar(32)
  ...
}

model User {
  ...
  @@unique([orgId, phone])   // 新增:同机构手机号唯一(phone 为 NULL 的行互不冲突,PG 语义)
}
```

迁移 SQL 要点(手写 `prisma/migrations/0005_org_code_login/migration.sql`,参考 0002/0004 风格):

1. `ALTER TABLE orgs ADD COLUMN code VARCHAR(32)` → **回填**现网机构(建议 `'QM' || id`,
   或运营指定的助记码)→ `SET NOT NULL` + `CREATE UNIQUE INDEX`。
2. users 复合唯一前**先查重**(执行时必须跑,不能跳):
   `SELECT org_id, phone, COUNT(*) FROM users WHERE phone IS NOT NULL AND deleted_at IS NULL GROUP BY 1,2 HAVING COUNT(*)>1;`
   有重则人工处置后再建约束。注意软删行:约束建在全表上,若历史软删行撞号,
   约束改用部分唯一索引 `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`(Prisma schema 里
   保留 `@@unique` 声明仅作文档,以迁移 SQL 的部分索引为准——0001 已有先例口径则从之)。

**phoneHash 取舍(记录决策依据)**:若将来真的落地「手机号应用层加密」,确定性加密才能查询/
约束——方案是加 `phone_hash CHAR(64)`(HMAC-SHA256(phone, `PHONE_HASH_KEY` env)),唯一约束
迁到 `[orgId, phoneHash]`,登录以 hash 定位、密文列仅供展示解密。**本方案按明文现状设计**,
不引入 phoneHash;上面的复合唯一在明文下即成立。加密是独立的后续工程(涉及存量回填与
脱敏展示),不要和多机构改造混在一波做。

### 3.2 契约(需批准;openapi.yaml + dto.ts + gen:sdk)

- `POST /auth/login` requestBody 加 `orgCode: string`(**必填**);
- `POST /auth/student/login` 同加 `orgCode: string`(必填);
- 错误语义:orgCode 不存在/停用与账号密码错误**统一回 401「账号或密码错误」**,
  不单独提示「机构不存在」(防机构码枚举;机构停用保留现有 403 文案则仅在账号验证通过后给出)。
- `Me` / token 形状零变化。

### 3.3 后端(auth 模块)

- `AuthService.login(orgCode, phone, password, ip)`:
  `org = findUnique({ code })`(大小写归一)→ 无/停用 → 401;
  `findFirst({ orgId: org.id, phone, role in [admin,teacher], ... })`(仍在 `runWithoutTenant`
  里跑,但 where 显式带 orgId——登录时尚无 ALS 租户上下文,这是既有口径)。
- `studentLogin(orgCode, studentNo, password, ip)`:同上定位 org 后
  `findFirst({ orgId, studentNo, role: 'student', deletedAt: null })` **唯一命中**,验一次密码;
  删除「候选列表逐个验密」循环。学习时段门禁/scrypt 静默升级/审计逻辑原样保留。
- `tools/init-prod.ts` 加 `--org-code` 必填参数(建机构时写入);`prisma/seed.ts` base 阶段
  给演示机构固定码(如 `QM001`),e2e fixtures 建 org 时带码。

### 3.4 前端(三端登录页)

- 登录表单加「机构码」输入框:localStorage 记住上次输入(key 各端独立,同 token.ts 口径);
  支持 URL 查询参数 `?org=QM001` 预填(机构可发专属登录链接,学生/家长少输一项)。
- `src/mocks/handlers.ts` 与 `data.ts`:登录 handler 校验 orgCode(mock 固定 `QM001`),
  错码回 401——保证 mock 与真实同形。
- 三端改动对称,涉及:`pages/Login*.tsx`(admin/teacher 共用手机号版、student 学号版)、
  登录调用处 body 加字段(契约类型自动红,跟着编译错误改即可)。

## 七、明确不做(本改造范围外)

- 机构自助注册(建机构仍走 init:prod / 运营后台)。
